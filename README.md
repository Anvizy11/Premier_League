# Premier League

Локальная система управления чемпионатом: Flask, Jinja2 и SQLite.

## Запуск

```bash
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m flask --app app init-db
python app.py
```

Сайт: http://127.0.0.1:5001. `init-db` выполняет повторяемую миграцию без удаления данных соревнования. Перед обновлением рабочей базы делайте резервную копию.

## Структура проекта

- `app.py` — короткая точка запуска; команда `python app.py` остаётся прежней.
- `premier_league/__init__.py` — фабрика `create_app`, подключение маршрутов и команд.
- `premier_league/routes/` — HTTP-обработчики по разделам: публичные страницы, вход, управление, протоколы, заявки, события, дисциплинарные решения.
- `premier_league/services/` — правила протокола, дисциплинарные расчёты, статистика, подтверждения и справочник судей.
- `premier_league/database.py`, `migrations.py`, `schema.sql` — соединения, миграция и схема базы.
- `premier_league/auth.py`, `cli.py`, `errors.py`, `paths.py` — доступ, команды, страницы ошибок и пути к файлам.
- `templates/` — страницы; `macros/` и `partials/` содержат общие элементы протокола.
- `static/js/` — отдельные скрипты поиска, заявок и событий; `static/css/` — стили.
- `scripts/` — служебное наполнение данных и прежние миграционные команды.
- `tests/` — интеграционные проверки и проверки сборки приложения.
- `docs/TODO.md` — исходные заметки о развитии, перенесённые из `.cursorignore`.

Рабочая база `premier_league.db`, ключ `.session_key` и папка `backups/` остаются в корне проекта. Их расположение не зависит от расположения Python-модулей. Существующие ссылки страниц и команды Flask сохранены. Рефакторинг не требует миграции рабочей базы.

Служебные скрипты запускаются **из корня проекта как модули**, например:

```bash
python -m scripts.generate_fixtures
```

Это не команда обычного запуска сайта: она изменяет базу, как и раньше. Для импорта модулей приложения используйте `premier_league.*`.

## Роли и аккаунты

```bash
python -m flask --app app create-user organizer --role organizer
python -m flask --app app create-user referee --role referee
python -m flask --app app create-user club_admin --role team_admin --team-id 1
```

Замените `1` на ID нужного клуба: он виден в адресе страницы команды `/teams/ID`. Каждому клубу создаётся отдельный аккаунт с его ID. Имя пользователя можно выбрать своё. Команда запросит пароль дважды; ввод скрыт, минимум 10 символов. Пароли сохраняются в виде хешей.

Вход: http://127.0.0.1:5001/login.

Для смены забытого пароля существующего аккаунта:

```bash
python -m flask --app app reset-password organizer
```

Замените `organizer` на нужное имя пользователя. Команда запросит новый пароль
дважды без отображения ввода. Минимум 10 символов; в базе обновляется только хеш
пароля, роль и данные аккаунта сохраняются. Старый пароль для этой команды не нужен.
Уже открытые сессии пользователя автоматически не завершаются.

- **team_admin** связан с одним клубом. Видит матчи своей команды, добавляет членов своего штаба и составляет только собственную заявку на игру.
- **referee** получает доступ только к назначенным ему предматчевым протоколам. Заполняет ФИО судьи, двух помощников и резервного, проверяет заявки, вносит события и замены, передаёт итоговый протокол организатору.
- **organizer** создаёт встречи, назначает судей, заполняет заявки обеих команд и судейскую бригаду, вносит события и замены, самостоятельно утверждает результат. Может также вернуть протокол судье и сохранять решения КДК. Проверки размеров заявок и дисциплинарного допуска обязательны и для организатора.
- Гости видят таблицу, клубы, игроков и утверждённые протоколы. Предматчевые заявки доступны участникам матча и организатору после входа.

При переходе с прежней модели аккаунты `admin` и `reviewer` становятся организаторами, сохраняя логины, пароли и ID. Они не получают доступ администратора какого-либо клуба. Аккаунты судей и клубов нужно создать отдельно.

Ключ сессий `.session_key` исключён из Git. Можно задать `PREMIER_LEAGUE_SECRET_KEY` через окружение. Встроенный сервер рассчитан на локальное использование.

## Предматчевый протокол

1. Организатор создаёт матч с датой/временем и назначенным аккаунтом судьи. Для существующих запланированных матчей назначение задаётся в самом протоколе.
2. Администратор каждого клуба добавляет недостающих сотрудников на странице своей команды. Роль задаётся свободным текстом. Обязательные роли: `Главный тренер` и `Врач`; также распознаются прежние `Head Coach` и `Doctor` без учёта регистра.
3. Каждый администратор выбирает игроков и штаб своей команды, сохраняет и отдельно отправляет заявку судье. Перед отправкой сначала сохраните текущие изменения формы.
4. Судья проверяет обе заявки и подтверждает каждую отдельно. Может вернуть заявку команде на доработку, пока нет событий матча.
5. После проверки заявок и заполнения судейской бригады судья ведёт события и замены. Затем отправляет итоговый протокол организатору.
6. Организатор утверждает результат. Только после этого результат, карточки и отбытые пропуски участвуют в расчётах.

Лимиты **на каждую команду**: 7–11 стартовых игроков, один стартовый вратарь (по пометке в заявке), 0–12 запасных, 2–10 членов штаба, включая главного тренера и врача. Запас выбирается явно; весь состав клуба автоматически не включается. Один человек не может быть одновременно стартовым и запасным. Отстранённого участника нельзя включить даже на скамейку или в штаб.

После отправки заявки её меняют только после возврата судьёй. Если события уже внесены, для изменения состава сначала удаляются события и замены. Для исправления итогового протокола организатор возвращает его в черновик. Заявки при этом остаются проверенными; если требуется их изменение, судья отдельно возвращает их клубам. Для старых протоколов с неполными составами потребуется подать и проверить заявки по новым правилам.

### Самостоятельное заполнение организатором

Организатор может пройти все шаги без смены аккаунта: выбрать и сохранить обе заявки, заполнить бригаду, внести события, передать протокол на согласование и утвердить его. Предварительные подтверждения заявок судьёй для этого сценария не требуются. Для каждой формы заявки организатора передаётся ID соответствующей команды. Организатор может добавлять сотрудников любому клубу.

После подготовки итогового протокола (статусы `PENDING_REVIEW` или `VERIFIED`) администратор каждой команды и назначенный судья нажимают «Подтверждаю корректность протокола». Это три независимые отметки; организатор не может поставить их от имени участников. Отсутствие отметок не блокирует утверждение результата организатором и отображается в протоколе. Прежний порядок работы команд и судьи также поддерживается.

Подтверждение относится к конкретному содержанию: составам, штабу, событиям, заменам, дате, назначению и ФИО судей. После изменения этих данных отметка становится неактуальной. Если содержание изменилось между открытием страницы и нажатием кнопки, подтверждение отклоняется до повторной проверки обновлённой страницы.

### Ввод составов и судей

В протоколе хозяева расположены слева, гости справа (на узком экране — друг под другом). Для каждой команды есть таблицы старта и запаса с тремя столбцами: игровой номер, фамилия и имя, важные пометки. При выборе номера подставляется игрок и наоборот. Поиск в списках работает по началу фамилии, имени или номера; стрелка открывает полный список. Повторный выбор одного игрока в старте или запасе запрещён.

Вратарь отмечается автоматически по амплуа `GK`; можно также назначить вратарём игрока другого амплуа. В стартовом составе должен быть ровно один отмеченный вратарь. Капитан выбирается вручную, не более одного в заявке. «Легионер» вычисляется автоматически: любое гражданство, кроме `Англия`/`England`, включая неизвестное, даёт эту пометку. Пометки вратаря и капитана сохраняются в заявке и участвуют в проверке подтверждений протокола.

Ниже находятся поля штаба: главный тренер первым, далее остальные сотрудники, включая обязательного врача. События скрыты до сохранения корректных заявок обеих команд и заполнения обязательной судейской бригады. Для роли судьи дополнительно требуются подтверждённые заявки. Организатор проходит сценарий самостоятельно.

Поля судей предлагают поиск по справочнику. Добавлены 12 реальных судей и помощников из [опубликованных назначений АПЛ](https://www.premierleague.com/en/news/4444029/match-officials-for-matchweek-9-in-premier-league-season-2025-26). Справочник ФИО не создаёт аккаунты и не выдаёт доступ. Прежние ФИО из сохранённых протоколов при миграции также добавляются в справочник.

VAR и AVAR находятся в сворачиваемом блоке под резервным судьёй; оба поля необязательны. Если они уже заполнены, блок открыт автоматически. Чтобы убрать назначение, выберите «Не назначен» и сохраните бригаду. Закрытие блока само по себе назначение не удаляет.

## Дисциплинарная статистика на главной странице

Рядом с вкладкой бомбардиров находится полный дисциплинарный реестр игроков и
штаба. Краткий реестр игроков сохраняется под турнирной таблицей. В колонках КК
и ЖК команд учитываются карточки игроков и штаба вместе, только из утверждённых
матчей. Участники без карточек и отстранений не загромождают реестр.

`services/cards.py` считает сезонные карточки независимо от текущего допуска:
две ЖК в одном матче учитываются только как одна КК (0 ЖК и 1 КК), а сами
события предупреждений сохраняются в протоколе. Они не идут в накопление пяти. После отбытия пропуска карточки и число отстранений остаются видны, а
статус меняется на «Допущен». В карточке игрока также отображается число
отстранений за сезон. Повторная корректировка срока одной санкции не создаёт
ещё одно отстранение.

Решение комиссии принимается вне сайта: организатор указывает общий срок и
основание через «Сохранить срок отстранения». Отдельного процесса заседания,
голосования или согласования КДК в приложении нет.

## Карточки и отстранения

- Одна ЖК в матче добавляет один матч в накопление. Каждые 5 таких матчей дают автоматический пропуск одной игры.
- Две ЖК в одном матче автоматически означают удаление и пропуск одной игры. Этот матч полностью исключается из накопления пяти; прежние предупреждения сохраняются. Отдельную прямую КК за вторую ЖК добавлять не нужно.
- Прямая КК означает удаление и автоматический пропуск минимум одной игры. Предыдущие ЖК сохраняются, включая единственную ЖК в этом же матче.
- Эти правила применяются к игрокам и членам штаба. Карточки могут получать также заявленные запасные и уже заменённые игроки. Удалённый запасной не может выйти на поле.
- Пропуск отбывается в следующем сыгранном матче своей команды, если участника нет во всей заявке. Засчитывается после утверждения результата. Запланированный матч или неутверждённый результат пропуск не погашает.
- Организатор указывает **общий срок** по решению КДК, минимум 1 игру, и основание. Уже отбытые пропуски учитываются, оставшийся срок увеличивается. Сохраняется история решений. Позднее решение применяется после последнего уже утверждённого матча команды: прежние обычные отсутствия не превращаются в отбытые пропуски.
- При нескольких санкциях сроки отбываются параллельно: одна пропущенная игра уменьшает каждый действующий срок. Это принятое техническое правило для одновременного порога 5 ЖК и прямой КК; если регламент требует сложения, его следует изменить отдельно.
- Старое поле ручной блокировки `is_suspended` сохранено и также запрещает включение в заявку; автоматические санкции вычисляются независимо от него.

Дисциплинарный порядок определяется датой и временем матча; для совпадающих значений — туром и ID. У перенесённых встреч организатор должен обновлять дату до внесения событий. Старые матчи без даты считаются более ранними и упорядочиваются по туру и ID; для корректной хронологии их даты потребуется восстановить отдельно. Все даты/время задаются в местном времени соревнования.

Допуск проверяется повторно при проверке заявки, внесении событий и утверждении результата. Если позднее утверждение старого матча сделает уже утверждённую следующую заявку недопустимой, система потребует сначала вернуть следующий протокол судье.

## Расчёт минут

Матч длится 90 минут, дополнительное время пока не поддерживается. События игроков, карточки штаба и замены отображаются в одной ленте по возрастанию минуты. В пределах одной минуты используется общий порядок добавления; он также учитывается при проверке нахождения игрока на поле. Для старых записей до введения общего порядка точная последовательность между разными типами событий не сохранена: миграция задаёт для них постоянный порядок. Удаление останавливает время игрока; две ЖК работают как удаление без отдельной записи КК. Удалённого игрока нельзя заменить, обратный выход заменённого запрещён. Лимит количества замен пока не задан. Неиспользованный запасной не получает сыгранный матч.

## Общий порядок событий

`premier_league/services/timeline.py` объединяет события в один список. Таблица
`match_timeline_order` хранит общий номер добавления для событий игроков, штаба
и замен. SQL-триггеры регистрируют добавление и удаление в той же транзакции,
поэтому откат ошибочного события откатывает и запись порядка. Точное время
добавления старых событий не восстанавливается; повторная миграция не меняет
уже назначенный порядок.

После обновления существующего сайта выполните `python -m flask --app app init-db`
с предварительной резервной копией базы, затем перезапустите сервер. Порядок
событий включён в подтверждаемую версию протокола; прежние подтверждения
потребуют повторной проверки участниками.

## Проверки

```bash
python -m unittest discover -s tests -v
```

Каждый тест использует отдельную временную базу, рабочая база не открывается тестами. Для иной рабочей базы задайте `PREMIER_LEAGUE_DATABASE` (предпочтительно абсолютный путь).

`scripts/seed_season_26_27.py` очищает данные чемпионата перед заполнением. Скрипты `scripts/enrich_nationalities.py`, `scripts/generate_fixtures.py` и `scripts/migrate_protocols.py` тоже изменяют выбранную базу; для обычного запуска они не нужны.

## Инструменты разработки

Форматирование Python выполняется Black; параметры заданы в `pyproject.toml`. Он устанавливается только в виртуальное окружение проекта:

```bash
python -m pip install -r requirements-dev.txt
python -m black app.py premier_league scripts tests
python -m black --check app.py premier_league scripts tests
```

Для запуска сайта достаточно прежнего `requirements.txt`. Дополнительные инструменты не нужны пользователю сайта.

## Резервная копия

```bash
mkdir -p backups
sqlite3 premier_league.db ".backup 'backups/premier_league_backup.db'"
sqlite3 'file:backups/premier_league_backup.db?mode=ro&immutable=1' 'PRAGMA integrity_check;'
```

Для каждой новой копии используйте новое имя. `immutable=1` применяйте только к неподвижной резервной копии. Базы и вспомогательные файлы исключены из Git.

## Добавление игроков и штаба

На странице команды вкладки «Игроки» и «Штаб» содержат отдельные формы. Их может заполнять организатор или администратор своей команды. Обработчики находятся в `premier_league/routes/people.py`, общая проверка данных и расчёт возраста — в `premier_league/services/people.py`, формы — в `templates/macros/people.html`, предварительный расчёт возраста в браузере — в `static/js/people.js`.

Для новых записей обязательна дата рождения. Возраст рассчитывается автоматически по текущей дате Europe/Istanbul и отдельно не хранится. Для старых записей без даты рождения отображается «—». Имя, фамилия и дата рождения определяют дубль во всех клубах: отдельно среди игроков и отдельно среди штаба. Проверка не учитывает регистр и лишние пробелы. Нельзя добавить игрока с уже занятым номером в своей команде; существующие номера миграция не меняет.

Для реальных участников сохранены ссылки на источники; основной справочник сопоставлен с набором Transfermarkt по внешним идентификаторам, отсутствующие и спорные записи проверены отдельно по профилям клубов, лиг и федераций. Написания имён, клубы, номера и протоколы импорт не меняет. Расхождения источников по Maalik Hashi и Nobel Mendy отмечены в поле `note`.

У 20 ранее сгенерированных врачей даты **условные**, назначены по просьбе пользователя для тестирования. Такие записи помечены `synthetic: true`; это не реальные биографические данные. Перед использованием проекта для настоящего турнира их нужно заменить реальными сотрудниками.

Повторяемый импорт выполняется скриптом `scripts/enrich_birth_dates.py`:

```bash
# Только показать количество предстоящих изменений:
python -m scripts.enrich_birth_dates
# Записать реальные даты с автоматической резервной копией:
python -m scripts.enrich_birth_dates --apply
# Включить также условные даты тестовых врачей:
python -m scripts.enrich_birth_dates --apply --include-synthetic
```

Скрипт заполняет только пустые даты, требует однозначного совпадения имени, фамилии и клуба и останавливается при конфликте с уже заполненной датой. Все обновления проходят в одной транзакции. Повторный запуск с тем же набором не меняет данные. База и резервные копии исключены из Git, а справочник и скрипт можно сохранить вместе с кодом.
